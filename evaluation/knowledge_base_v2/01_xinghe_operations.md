# 星河项目总体运维规范

## 1. 文档说明与适用范围

本文档定义星河项目的总体运维要求，适用于参与星河项目生产环境日常巡检、变更、监控、备份与故障处理的全体工程师。星河项目是公司的核心生产业务系统，任何操作必须以「业务连续性优先、变更可控、责任可追溯」为基本原则。

本文档是总体性规范，具体操作细则由下列专项规范承接：

- 数据库备份与恢复：《数据库备份与恢复管理规范》
- Redis 部署与运维：《Redis 部署与运维规范》
- 服务器部署与日常运维：《服务器部署与日常运维规范》
- 权限与安全审计：《权限控制与安全审计规范》
- 故障响应与升级：《生产故障响应与升级规范》

涉及故障升级路径与责任归属的，统一按《生产故障响应与升级规范》执行，本文只做原则性描述。

## 2. 术语

| 术语 | 说明 |
| --- | --- |
| 生产环境 | 承载真实业务流量的运行环境 |
| 测试环境 | 用于功能验证与发布前回归的运行环境 |
| 变更窗口 | 允许执行可能影响业务的变更操作的时间段 |
| 事件单 | 用于登记、跟踪故障与异常的工作项 |
| 持久化 | 将内存数据写入磁盘以便重启后恢复的机制 |
| 灰度发布 | 先将新版本发布到少量节点观察，再逐步放量的发布方式 |
| 巡检 | 按固定频率对系统健康状态进行的例行检查 |

## 3. 系统构成

星河项目由以下核心组件构成，各组件相互依赖，任一组件异常都可能影响整体业务：

- 应用服务器：承载业务逻辑与对外接口，是流量的直接入口。
- 数据库：承载核心业务数据的持久化存储，是数据一致性的根本保障。
- Redis：承载缓存和部分会话状态，用于降低数据库压力与加速访问。
- 日志：记录应用与系统运行轨迹，是排查问题与安全审计的重要依据。
- 监控：采集指标并触发告警，是发现问题的第一道防线。

上述组件中，数据库备份与 Redis 持久化是两个不同概念，不得混用或互相替代。

## 4. 环境与部署

| 环境 | 机房 | 说明 |
| --- | --- | --- |
| 生产环境 | A3 机房 | 承载真实业务流量，操作需审批 |
| 测试环境 | B1 机房 | 发布前回归验证，操作相对宽松 |

生产环境与测试环境在物理上隔离，网络、权限、操作流程与监控策略均不同，具体见《服务器部署与日常运维规范》。生产环境的所有变更，一律不得在测试环境未经验证的情况下直接执行。

## 5. 数据库备份

星河项目生产数据库每日凌晨 2:30 执行备份。备份策略、保留周期、恢复前检查与工单要求详见《数据库备份与恢复管理规范》。

业务高峰期间禁止直接执行数据库结构变更；结构变更必须在变更窗口内、经过审批后执行。备份任务是否正常完成，是每日巡检的必查项之一。

## 6. Redis 用途与边界

Redis 用于缓存和部分会话状态。其部署方式、持久化策略与容量管理详见《Redis 部署与运维规范》。

需要特别强调：Redis 的持久化（快照与 AOF）解决的是「内存数据重启后恢复」的问题，与「数据库备份」解决的是「业务数据灾难恢复」的问题，二者不是同一个概念。

## 7. 监控规则

| 指标 | 告警阈值 | 处理要求 |
| --- | --- | --- |
| CPU 使用率 | 连续 5 分钟 > 85% | 告警并通知值班工程师，定位高负载进程 |
| 内存使用率 | > 90% | 告警；持续 > 95% 需评估是否重启相关服务 |
| 磁盘剩余空间 | < 20% | 告警；< 10% 需立即清理或扩容 |
| Redis 内存使用率 | > 75% | 告警，排查大 key 与过期策略 |

监控告警统一通过企业微信推送给值班工程师；告警规则由监控专项负责维护。告警按严重程度分为「警告」与「严重」两级，严重告警必须立即响应。

## 8. 巡检

值班工程师每日执行例行巡检，巡检内容包括：

- 数据库备份任务是否正常完成；
- Redis 主从同步是否正常；
- 服务器 CPU、内存、磁盘使用率是否在阈值内；
- 应用日志是否有异常报错。

巡检发现异常，应及时登记并跟进处理，不得搁置。

## 9. 变更管理

生产环境变更必须提前申请，安排在变更窗口内执行，并遵循以下原则：

- 变更前必须评估影响面与回滚方案；
- 变更必须经过审批；
- 变更后必须验证核心链路是否恢复正常。

数据库结构变更、服务器重启等高风险操作，额外要求有第二人复核。新版本发布优先采用灰度发布方式，观察无异常后再全量放量。

## 10. 容量管理

各组件应定期评估容量，避免资源耗尽引发故障：

- 数据库存储容量按业务增长定期评估；
- Redis 内存容量按缓存体量评估；
- 服务器磁盘容量按日志与数据增长评估。

容量不足时，应在变更窗口内完成扩容或清理，不得等到告警后才被动处理。

## 11. 故障升级

发生故障时，值班工程师应按《生产故障响应与升级规范》进行分级、登记事件单并升级。故障分级、响应时限与责任矩阵以该规范为准。

## 12. 责任边界

各组件（数据库、Redis、服务器、安全）的操作责任边界分别由对应专项规范定义；涉及跨组件的责任归属，按项目责任矩阵执行。
