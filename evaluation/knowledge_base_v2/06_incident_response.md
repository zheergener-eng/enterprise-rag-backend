# 生产故障响应与升级规范

## 1. 文档说明与适用范围

本文档定义生产故障的分级、响应、升级与复盘要求，适用于值班工程师、数据库管理员、运维负责人与安全人员。本文描述角色与流程。

## 2. 术语

| 术语 | 说明 |
| --- | --- |
| P1 | 影响核心业务、需立即处理的最高优先级故障 |
| P2 | 影响部分业务或存在较大风险的中等优先级故障 |
| P3 | 影响较小、可计划处理的低优先级故障 |
| 事件单 | 登记故障、跟踪处理过程的工作项 |
| 复盘 | 故障处理完成后对根因与改进措施的分析 |
| 升级 | 将故障上报给更高层级角色处理 |

## 3. 故障分级与响应时间

| 级别 | 定义 | 响应时间要求 |
| --- | --- | --- |
| P1 | 核心业务中断或数据安全受影响 | 立即响应并升级 |
| P2 | 部分功能异常或存在较大风险 | 1 小时内响应 |
| P3 | 影响较小、可计划处理 | 24 小时内响应 |

故障级别由值班工程师根据影响范围与业务损失判定，必要时可上调级别。

## 4. 故障分级示例

为便于值班工程师快速判定，给出如下示例（示例仅作参考，最终以影响范围为准）：

- 数据库不可用、核心业务完全中断 → P1；
- Redis 主节点故障导致部分功能降级 → P2；
- 单台服务器风扇告警、暂不影响业务 → P3。

## 5. 事件单要求

数据库、Redis、服务器故障均需要创建事件单，记录以下字段：

- 故障编号与发生时间；
- 故障级别；
- 影响范围与现象；
- 处理过程与结果；
- 处理人与状态。

事件单全程跟踪，直至故障关闭。

## 6. 事件单生命周期

事件单状态依次流转：新建 → 处理中 → 已解决 → 已关闭。每个状态变更需记录时间与操作人，确保全程可追溯。

## 7. 升级要求

- P1 故障需要立即升级；
- P2 / P3 故障按响应时间窗口处理，超时未解决需逐级升级。

升级路径依次为：值班工程师 → 数据库管理员 / 运维负责人 → 更高层级。具体责任人按项目责任矩阵执行。

## 8. 数据库备份失败处理

数据库备份失败属于需要登记和升级的异常场景。值班工程师发现备份失败后，应登记事件单并按本规范升级，不得因「次日自动重跑」而忽略。备份失败的责任归属按项目责任矩阵执行。

## 9. 组件故障处理

- Redis 主节点故障：按《Redis 部署与运维规范》执行主从切换，切换后验证读写。
- 服务器宕机：按《服务器部署与日常运维规范》执行重启与恢复，登记事件单。
- 数据库故障：登记事件单，评估影响并组织恢复。

## 10. 复盘要求

故障处理完成后必须进行复盘，复盘内容包括：

- 根因分析；
- 影响范围评估；
- 改进措施与责任人；
- 改进措施落地跟踪。

复盘结论应记录在案，重大故障复盘结果需通报相关团队。

## 11. 值班与演练

生产环境实行值班制度，值班工程师负责接收告警与初步处置。告警统一通过企业微信等渠道通知值班工程师。定期组织故障演练，检验响应流程与人员配合是否到位。值班工程师无法处置故障时，应按升级路径联系对应角色。值班交接时需交接未处理的告警与事件单，确保处理不中断。

## 12. 责任边界

本文描述的角色包括值班工程师、数据库管理员、运维负责人与安全人员。具体的责任归属与审批流程，按项目责任矩阵执行。

## 13. 响应处理流程

值班工程师接收告警后，按以下流程处理：

1. 确认故障现象与影响范围；
2. 判定故障级别并创建事件单；
3. 按级别要求响应，必要时升级；
4. 处置完成后关闭事件单并组织复盘。

## 14. 应急联系

值班工程师无法独立处置故障时，应按升级路径联系对应角色。各角色的值班安排与联系方式见值班表。

## 15. 故障报告

重大故障处理后，需形成故障报告，包含故障时间、影响范围、根因、处理过程与改进措施。故障报告应归档并通报相关团队，作为经验沉淀供后续同类故障参考。
